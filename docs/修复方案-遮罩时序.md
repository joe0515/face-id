# 修复方案：全屏遮罩时序 + 关应用时误认证

> 状态：**已实施**（2026-10-18 20:34 完成构建 / 测试 / 打包 / 安装）
> 提出：2026-10-18
> 相关验收项：R21 / R22；历史修复见 `docs/验收测试清单.md`

---

## 1. 报告的现象

| # | 现象 | 期望 |
|---|---|---|
| A | 打开被锁的软件时**先显示软件界面，随后才被遮罩**；全屏遮罩「消失」了 | 从第一帧起就被遮住，看不到 App 界面 |
| B | 关闭其中一个被锁应用时，**弹出另一个应用的认证**（即此前的「关照片弹微信」） | 只挑战真正在前台显示内容的应用 |

---

## 2. 排查结论（代码级）

### 2.1 现象 A 的根因：应急遮罩被「窗口探测」推迟了

`AppUnlockCoordinator.handleLockedAppDetected`（`FaceID/Coordination/AppUnlockCoordinator.swift:155-198`）现在的逻辑是：

```
检测到被锁 App 到前台
  → shield.hasOnScreenWindow(pid) == false？          ← 冷启动时窗口还没建，必然为 false
      → 起 windowProbeTask，每 40ms 轮询，直到 CGWindowList 报告窗口 onScreen
      → 这时才 beginChallenge()                      ← imposeEmergencyCover() 在这里面才被调用
```

而 `imposeEmergencyCover`（全屏应急遮罩）只在 `beginChallenge` 内调用（`AppUnlockCoordinator.swift:221-227`）。

**后果**：冷启动打开被锁 App 时，轮询要等到「窗口已经画出来」才会铺全屏遮罩 —— 用户先看到 App 界面一瞬，然后才被遮。这正是现象 A。

这是**修现象 B（上一轮）时引入的副作用**：修 B 之前，`imposeEmergencyCover` 是在检测通知的**同步回调**里立即执行的（`isFreshLaunch` 为 true 时即使没有窗口也盖），所以冷启动从第一帧就是遮住的。

### 2.2 现象 B 的根因：它靠「窗口探测」兜住，方案不能把它拆掉

R22 场景（照片 + 微信都被锁）：

```
解锁照片 → 关闭照片 → macOS 把微信切到前台（微信窗口早已 orderOut，CGWindowList 全 isOnScreen=false）
  → handleAppEvent → hasOnScreenWindow(微信) == false
  → windowProbeTask 轮询 0.45s，期间始终无窗口 → 安静放弃（不弹面板、不铺遮罩、不隐藏）
```

**当前 B 是好的**。但如果为了修 A 简单地把 `imposeEmergencyCover` 挪回同步回调，就会对「没有窗口的微信」铺满全屏遮罩并弹出认证 —— B 立刻回归。

**A 与 B 本质冲突，不能二选一，必须分流。**

### 2.3 现象 A 的第二处嫌疑（60ms 竞态）

`WindowShieldManager.syncPanels` 末尾无条件调用 `dismissEmergencyCoverAfterMinimumOnScreen`（`WindowShieldManager.swift:342-391`）。它只保证应急遮罩**已显示 ≥ 60ms**，不保证窗口遮罩**已经合成**。新建 panel 的 `makeKeyAndOrderFront` 在同一 runloop turn 完成，若窗口服务器还没画出来就撤掉全屏遮罩，会出现：

```
全屏遮罩 → 撤掉 → （空隙）露出 App 界面 → 窗口遮罩才上
```

这对应现象 A 的另一种描述（「全屏遮罩消失」）。两处都要修。

---

## 3. 方案

### A. 检测回调内按「是否即将出窗口」三分流（核心）

改写 `handleLockedAppDetected`，在**同步回调**内就决定：

| 分支 | 判据（同步可查） | 动作 |
|---|---|---|
| ① 有屏上窗口 | `hasOnScreenWindow(pid) == true` | 立即 `beginChallenge`（现状不变） |
| ② 冷启动 / 即将出窗口 | 无屏上窗口，且 **`launchDate` 距今 < `freshLaunchThreshold`(5s)**；`launchDate == nil` 时以「CGWindowList 里该 pid 完全没有窗口」兜底 | 立即 `beginChallenge`（含 `imposeEmergencyCover(isFreshLaunch: true)`），**不等探测**；由 `shield()` 的 `settleForWindows(0.35s)` 自然等窗口出现后转窗口遮罩 |
| ③ 已运行但窗口全离屏 | 无屏上窗口、且不满足②（典型：微信关窗留后台） | 保持现状：`windowProbeTask` 轮询 0.45s，出现窗口才 `beginChallenge`，否则安静放弃 |

**效果**：
- 冷启动 → 恢复「第一帧即全屏遮罩」，App 界面不可见（修 A）
- 关照片激活微信 → 微信 `launchDate` 是几小时前、且 CGWindowList 仍有 4 个离屏窗口 → 走分支③ → 安静放弃（B 不回归）

**分支②的阈值与信号**：
- `freshLaunchThreshold = 5.0`（沿用 `beginChallenge` 内原有硬编码 5s，提取为 `FIDConstants.freshLaunchThreshold`）
- `launchDate` 是**权威信号**；「完全没有窗口」只在 `launchDate == nil` 时兜底
- ⚠️ **实施时收紧了判据**（原方案写的是「任一信号满足即算冷启动」）：若把「完全没有窗口」也当成冷启动信号，那么「关窗后窗口真的被销毁」的应用（不像微信只是 orderOut）会被误判 → 对无窗口的应用弹认证，B 回归。所以 `launchDate` 非空时只认它，非空即不可能误判
- `launchDate == nil` → 用「完全没有窗口」兜底；连窗口也没有却 launchDate 老 → 仍走③（保守，宁可漏也不打扰）

### B. 应急遮罩撤销改为「确认窗口遮罩已合成」（治 60ms 竞态）

`dismissEmergencyCoverAfterMinimumOnScreen` → `dismissEmergencyCoverWhenReady`：

```
撤销条件 = 已显示 ≥ emergencyCoverMinimumOnScreen(60ms)
        && !panels.isEmpty
        && panels 全部 isVisible
不满足 → 等一帧（DispatchQueue.main.async）重查
重查到 emergencyCoverMaxWait(0.5s) 为止 —— 超时必须撤，不能无限挡屏
```

- 新增常量 `emergencyCoverMaxWait = 0.5`
- 需要记录遮罩建立时刻的上界（`emergencyCoverDeadline`）用于超时

### C. `switchToHidden` 的顺序微调

现为 `dismissEmergencyCover()` → `app.hide()`（`WindowShieldManager.swift:436-453`）。改为**先 `app.hide()` 再撤遮罩**，消掉「遮罩撤了、App 还没隐藏」的一帧空隙。

### D. 探测步长 40ms → 16ms

分支③的轮询间隔（`AppUnlockCoordinator.swift:189`）降到 16ms（约一帧），让「Dock 重开微信、窗口重建」这类场景更快接住，缩短用户可见的界面时间。新增常量 `windowProbeInterval = 0.016`。

### E. 新增 / 提取常量（全部进 `FIDConstants`）

| 常量 | 值 | 用途 |
|---|---|---|
| `freshLaunchThreshold` | 5.0 | 分支②的冷启动判定 |
| `windowProbeInterval` | 0.016 | 分支③轮询步长 |
| `emergencyCoverMaxWait` | 0.5 | 分支 B 的撤销超时 |

## 4. 边界与风险评估

| # | 边界 | 处理 |
|---|---|---|
| 1 | 分支②把「前台 5 秒内没有窗口」的 App 当成冷启动 → 铺遮罩后 `settleForWindows` 失败 → `switchToHidden` 隐藏 | 既有冷启动行为（挡住优先于露出），保持；`didLaunchApplication` 已有 `app.isActive` 门禁，非前台启动不会进来 |
| 2 | 用户**主动从 Dock 打开已在后台的微信**（窗口重建） | `launchDate` 老 → 走分支③ → 窗口出现后挑战，界面会可见一瞬。这是「用户主动打开」的正常场景，与关照片的误触发不同，接受 |
| 3 | `launchDate == nil` | 用「完全没有窗口」兜底判冷启动 |
| 3b | 「关窗后窗口真的被销毁」的应用（launchDate 老、CGWindowList 为空） | `launchDate` 非空且老 → 走③，**不会**被误判成冷启动（实施时收紧的判据，见上） |
| 4 | 冷启动遮罩盖哪块屏 | 无窗口时用鼠标所在屏（`screenUnderMouse`，Dock 点击时即 Dock 屏）；窗口出现后窗口遮罩在正确屏盖上并撤销应急遮罩 |
| 5 | 分支 B 超时（0.5s）时窗口遮罩仍不可见 | 撤全屏遮罩、保留窗口遮罩 panel（可能延迟出现）。0.5s 已远超正常合成时间，仅作兜底 |
| 6 | 设置里若选「隐藏应用」而非「窗口遮罩」 | 走 `switchToHidden`，与本次改动无关（App 直接隐藏，用户看不到界面） |

## 6. 第二轮：微信仍会先露界面（2026-10-18 21:08 追加）

### 现象
照片（冷启动）修好了；**打开微信仍没有全屏遮罩、会短暂看到窗口才被遮罩**。

### 排查（取证，不是猜）
- 读了原项目 `FaceGate-Mac-main/FaceGate/Core/AppLocker.swift`：`blockApp` 的 **Step 1 就是同步 `runningApp.hide()`**，然后才 `showOverlays`。原项目**不存在**「先看到界面」的问题 —— `hide()` 在同一 runloop turn 生效，下一帧系统直接不画这个 App 的窗口。
- 我们的策略是「窗口遮罩为主」，遮罩是**窗口级**的，要靠窗口服务器合成：从 `didActivate` 通知到遮罩真正画出来之间总有几帧窗口期。照片没问题只是因为它是**冷启动**，分支②在窗口还没建时就铺了全屏遮罩。
- 探针实测（`CGWindowList`，无需权限）确认：**`hide()` 之后窗口数量与 `bounds` 完全保持，只有 `isOnscreen` 变 false** —— 也就是说隐藏后仍拿得到几何，隐藏与窗口遮罩不互斥。
- 同时实测确认微信当时**有 1 个可见窗口**（只是被别的 App 盖住）→ 走分支①，遮罩铺了但仍有窗口期，与用户描述一致。

### 改动（照原项目方案，与我们的窗口遮罩结合）
1. **`beginChallenge` 增加同步 `runningApp.hide()`**（原项目 Step 1）
   - 顺序：先 `imposeEmergencyCover`，**再** `hide()`。不能反 —— `imposeEmergencyCover` 的守卫看的是隐藏前的窗口状态，hide 之后 `kCGWindowIsOnscreen` 全变 false，遮罩会被自己的守卫挡掉
   - hide 之后补一次 `NSApp.activate(ignoringOtherApps: true)`（原项目同样这么做）：hide 会让 macOS 异步把焦点让给下一个 App，不抢回来挑战面板会随即丢掉键盘
2. **`shield()` 返回 `.windowShield` 时立刻 `runningApp.unhide()`**：遮罩已 `orderFront` 且取了 key，此时把 App 放回来，它画在遮罩**下面** —— 用户看到「窗口被盖住」，而不是原项目那种「App 直接消失」。只有 `shield` 回落隐藏时才保持 hidden
3. `windowProbeInterval` 0.016 → **0.008**（半帧）

### 仍未消除的边界
- **分支③（已运行 App 的窗口重建，如 Dock 点开已关窗的微信）**：挑战要等探测发现窗口才发起，从「窗口已合成」到「我们铺上遮罩」仍有窗口服务器批处理 + 轮询的延迟（约 20–50 ms）。要归零只能在探测期就 hide，而 hide 会让 `hasOnScreenWindow` 永远为 false、探测失效，且会误伤「系统连累激活」的场景（R22）。列为已知限制
- **hide 之后 AX 是否仍可读未实测**（命令行进程无辅助功能授权，测不了）：若读不到，`shield` 的 `settleForWindows` 会超时并回落到隐藏模式 —— 行为仍然正确（不露界面），只是从「窗口遮罩」降级成「App 消失」。这是可接受的退路，且用户一眼就能看出差别

### 验收
| # | 步骤 | 期望 |
|---|---|---|
| V1 | 锁定「照片」→ 从 Dock / Launchpad / 聚焦 打开照片 | **第一帧就是全屏遮罩**，App 界面全程不可见；窗口就绪后平滑转为只遮照片窗口的窗口遮罩（不再出现「先显示界面再被遮罩」） |

## 7. 第三轮：「界面一闪就消失、认证后还要去 Dock 重点开」（2026-10-18 21:40 追加）

### 现象
打开微信 → **界面一闪就消失**，只看到一瞬间的全屏遮罩，然后是刘海区域的人脸认证；**认证通过后微信界面不显示，要重新点 Dock 才出来**。

这正是上一轮预留的 R29 分支被触发，根因链条完整闭合：

```
beginChallenge: imposeEmergencyCover → hide()        ← 窗口从屏上消失（这是对的）
  → shield(): tracker.start() 返回 true，但 AX 读不到任何窗口
  → settleForWindows() 轮询 0.35s 全是空
  → switchToHidden("没有可覆盖的窗口")                ← 撤掉应急遮罩、App 保持隐藏
  → mode == .hidden → 不 unhide()
  → 认证通过 → unlockCurrentApp(): unhide() + activate()
     · activate() 在 macOS 14+ 由系统决定是否生效，对「窗口被 orderOut」的应用常常什么都不做
     · 于是用户看到的就是「要去 Dock 重点开」
```

### 取证
- 探针实测 `unhide()` 本身**能**让窗口恢复可见（hide 后可见 2→0，unhide 后 0→2）——所以问题不在 unhide，而在**它被跳过 + activate 不负责把窗口放回来**
- 上一轮已实测 `CGWindowList` 在 hide 后仍报告完整 bounds —— 这就是兜底的几何来源

### 改动
1. **`WindowShieldManager.onScreenWindows(for:)`**：协调器在 hide **之前**抓一份屏上窗口快照
2. **`shield(..., cachedWindows:)`**：AX 的 settle 等空时，若快照非空且不含全屏窗口 → 用快照的 bounds 直接建遮罩面板（`cachedPanels`，独立于 AX 驱动的 `panels`），返回 `.windowShield`
3. 于是 `blockThenAuthenticate` 照旧执行 `unhide()` —— hide 只持续几十毫秒，窗口根本没机会被销毁，且遮罩已经在那儿
4. **AX 接手无缝替换**：unhide 后 tracker 的轮询/AX 恢复 → `handleTrackerChange` → `syncPanels` 开头 `dismissCachedPanels()` 再建 AX 面板（同一组矩形，替换不可见）
5. **`handleTrackerChange` 防抖**：AX 刚恢复的那一两轮空读不再直接 `switchToHidden`（否则会把刚救回来的 App 又藏回去）—— 有空快照遮罩在时就当它是「AX 还没跟上」
6. **新增 `AppWindowPresenter`**：`unlockCurrentApp` 在 `unhide()` + `activate()` 之后，用 AX 明确 `AXMain` / `AXFocused` / `AXRaise` 主窗口 —— `activateIgnoringOtherApps` 在 macOS 14+ 已被系统忽略，这是唯一可靠的恢复手段
7. 配套：`shieldedWindowCount` / `restoreKeyPanel` / `dismissEmergencyCoverWhenReady` 的 readiness 判定都把快照遮罩算进去；`teardownPanels` / `switchToHidden` 都会撤掉它
