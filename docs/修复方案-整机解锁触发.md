# 修复方案：整机解锁「经常拉不起人脸认证」

> 状态：**已实施**（2026-10-24 21:24）
> 触发：用户反馈「软件在电脑屏幕打开时拉起人脸认证解锁电脑还是有问题，经常无法拉起认证界面，而原 glance 几乎不会有这个问题」

---

## 1. 与 glance 最新源码的逐层对比结论

用用户提供的最新 glance 源码（`/Users/joe/Downloads/glance-main`，commit `b97f521`）逐文件比对：

| 层 | glance | Face ID | 结论 |
|---|---|---|---|
| 信号源 `LockMonitor` | `screenIsLocked` / `screenIsUnlocked` / `screensaver.didstop` / `willSleep` / `screensDidWake` / `didWake` + `CGSessionScreenIsLocked` 复核 | **完全相同**，另加 `isDisplayAsleep` + `reconcileSleepState()` | 我们更强 |
| 触发判定 `FaceUnlockCoordinator` | 事件后一次性探测（300 ms） | **6 秒轮询**（24 × 250 ms，解锁即停） | 我们更强 |
| 刘海面板 `arm/disarm/beginScanning` | — | 相同 + AppLock 增量（`onAppLockCancel`、Esc） | 等价 |
| 会话门禁 `isSessionUnlocked` | 有 | 有 | 等价 |
| 相机 `CameraArbiter` | 无（直接 `camera.start()`） | 新增租约，`systemUnlock` 优先级 40 最高 | 我们新增，逻辑正确 |

**代码层面没有退化。** 但比对过程中定位到两个真实的缺陷机制，都在我们这一侧被放大：

### 缺陷 1：arm 之后立刻停止探测（`scheduleTriggerEvaluation`）

```swift
if LockMonitor.isScreenActuallyLocked() {
    self.evaluateTrigger()
    if self.hasArmedForCurrentLock { return }   // ← arm 即停
}
```

`arm()` 是在 `evaluateTrigger` 里 **250 ms 延迟**的 Task 中执行的。这 250 ms 内机器可能已被用户用密码解锁、`arm()` 自己的 `isScreenActuallyLocked` 复核可能失败、`cameraArbiter.acquire` 可能被拒、`camera.start()` 可能报错 —— 任何一种都让本次锁定**再也不 arm**，且没有任何自动重试。

### 缺陷 2（主因）：`hasArmedForCurrentLock` 依赖一条可能丢失的通知

这个一次性标志只在两处重置：
1. `evaluateTrigger` 发现机器**未锁定**时（依赖 `screenIsUnlocked` 分布式通知）
2. 收到新的 `.wake` 事件且不在 2 秒 burst 内

glance 自己的 `LockMonitor` 注释就写着：这类分布式通知**可能在进程被挂起时丢失**（合盖睡眠正是进程最可能被挂起的时刻）。一旦 `screenIsUnlocked` 丢掉，标志永远为 `true`，之后**每一次唤醒都被 `guard !hasArmedForCurrentLock` 静默挡掉** —— 表现为「经常无法拉起认证界面，直到重启 Face ID 才好」。这与「偶发、持续、重启后恢复」的现象完全吻合。

---

## 2. 改动

### A. 探测循环不再「arm 即停」

跑满 24 次（6 秒），期间由 `isAttemptInFlight` 防止重复 arm。arm 失败的后几轮会自然重试。

### B. `hasArmedForCurrentLock` 只在「尝试确实还在进行」时才生效

```swift
private var isAttemptInFlight: Bool {
    scanTask != nil || autoRetryTask != nil || NotchOverlayController.shared.phase == .scanning
}
```

扫描结束、自动重试结束、面板回到静止态之后，本次锁定**允许再次 arm** —— 不依赖 `screenIsUnlocked` 通知。这也顺带修掉缺陷 1：arm 失败后 250 ms 内的后续轮次会重试。

另外，250 ms 延迟后若发现机器已解锁，明确把 `hasArmedForCurrentLock` 复位并记日志（以前是静默留着 true）。

### C. 新增诊断日志 `UnlockDiagnostics`

`~/Library/Application Support/Face ID/diagnostics.log`，记录触发链的每一步：事件到达、探测读到的锁状态、每个 guard 的放弃原因、arm / 相机租约 / 相机启动结果。512 KB 滚动上限，纯文本。

**设置 → 常规 → 诊断 → 「导出诊断日志…」**（NSSavePanel，可附加到问题反馈里）。

> 之所以加日志：触发链上**每一步失败都是静默的**（只写一个用户在设置页看不到的 `statusMessage`）。「没有事件到达」和「事件到达但被 guard 挡掉」从外表完全无法区分，而这是这类偶发问题唯一可靠的定位手段。

## 3. 验收

| # | 步骤 | 期望 |
|---|---|---|
| V1 | 锁屏 → 唤醒，连续 10 次 | 每次都能拉起人脸认证（含此前「要重启才好」的那些情况） |
| V2 | 唤醒后不认脸、手动输密码解锁 → 再锁屏 → 再唤醒 | 仍然能拉起（缺陷 2 的回归验证） |
| V3 | 唤醒后 0.2 秒内用密码解锁 | 不出现残留面板；下次唤醒正常触发 |
| V4 | 设置 → 常规 → 诊断 → 导出日志 | 得到文本文件，能看到「事件 / evaluateTrigger / arm / 相机已启动」各行 |
| V5 | 若仍复现：把日志发回来 | 日志会直接指出是「没有事件」还是哪一条 guard 挡的（目前最可疑的是「会话处于锁定状态」） |

## 4. 已知未覆盖

- **会话锁定的静默失败**：若启动时那次触控 ID 验证被取消，`isSessionUnlocked == false`，之后所有唤醒都会被这条 guard 挡掉，且界面上没有任何提示。日志现在会明确记录它；如果 V5 的日志显示就是这条，下一步给它加可见提示（状态栏或刘海）。
- 分布式通知在合盖睡眠期间丢失是 macOS 的固有行为， glances 与我们都只能靠「权威状态复核」缓解；本方案的 `isAttemptInFlight` 就是让复核失败不再有持久副作用。
